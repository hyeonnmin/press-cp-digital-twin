## 2026-10-01 — 기존 합성 데이터 정리와 숫자 빛번짐 강화

- 사용자 요청: synthetic dataset 전체 삭제, outputs 정리, 너무 선명한 숫자 Crop의 빛번짐 강화.
- 정리: 기존 `datasets/synthetic` 전체 Run과 outputs의 과거 합성 렌더·Crop·로그를 삭제한다. `config/slot_crop_comparison.json`이 입력으로 참조하는 `outputs/phase2_reference`와 기존 도구 폴더 `outputs/tools`는 유지한다. 원본 실영상·코드·Config·USD Asset은 정리 대상에서 제외한다. 과거 문서의 검증 결과는 이력으로 보존하되 산출물 삭제 사실을 표시한다.
- 렌더: 공통 FFT Bloom scale `0.1 → 0.4`, cutoff `0.2 → 0.5`, isotropic falloff `50 → 5`. 강도만 올렸을 때의 넓은 배경 밝아짐을 줄이고 숫자 주변 확산을 늘리는 시각 조정이다. 랜덤화 범위나 실측 렌즈 복원값으로 취급하지 않는다. 숫자 형상·정답 문자열·기존 bbox 정의는 유지한다.
- 저장: 빛번짐 비교 검증은 `--output-root`로 `outputs/bloom_check/runs`에 한정했고 당시 학습 데이터 루트는 비워 두었다. 이후 사용자의 2프레임 추출 요청에 따라 현재 설정으로 `datasets/synthetic/cp_training/20261001T064808_756110Z`를 생성했다. 비교용 출력과 학습용 Run을 구분하며 같은 Seed의 중복 숫자 조합을 별도 독립 샘플로 합치지 않는다.


## 2026-10-01 — Panel 단위 YOLO Slot 검출 데이터 추가

- 확인: 사용자가 온도·압력·진공 표시기 3개로 구성된 예시 Crop을 제시하며 Panel별 이미지와 Slot bbox 생성 코드를 요청했다. 클래스는 사용자 확인에 따라 단일 `slot`으로 정했다.
- 결정: Panel당 주요 숫자 6개를 검출 객체로 삼는다. YOLO 라벨은 숫자 값 대신 클래스 0을 사용하고, 소수점 포함 정답 문자열·Slot ID는 별도 메타데이터에 보존한다. 작은 고정 보조 표시와 버튼은 대상에 포함하지 않는다.
- 범위: 기존 Recognition 데이터에 Detection 학습용 내보내기를 추가한다. 모델 설치·학습과 실제 영상 성능 평가는 이번 범위에 포함하지 않는다. 기존 개요의 기본 범위를 사용자 요청에 따라 데이터 생성까지 확장했다.
- Crop 근거: 신규 Run은 실제 USD Housing 경계를 기록한다. 이전 Run은 해당 Run의 Config로 경계를 복원하되 기존 42개 Slot ROI와 일치하는 경우에만 허용한다. 검출 bbox는 기본적으로 기존 숫자 bbox(4픽셀 여백 포함)를 사용하며 원본 좌표에서 Panel 좌표로 변환한다.
- 분할: 기본 Synthetic Train/Validation 80/20, Seed 42. 같은 원본 전체 프레임의 Panel 7개는 같은 Split에 둔다. 이유는 동일 프레임이 학습과 검증 양쪽에 섞이는 것을 막기 위함이다. Real Test 분할을 변경하지 않는다.
- 영향: 독립 변환 CLI와 새 생성기의 `--export-yolo`를 제공한다. 이미지/TXT/YAML과 원본 연결 JSONL·Hash·코드 버전을 기록하고 역변환·Crop 픽셀·Frame 분할을 검증한다. 현재 사용자 선택은 단일 클래스이며 Config에는 필요시 6종 Slot 구분 옵션도 제공한다.

## 2026-10-01 — 프레임 단위 학습 데이터와 정면 중앙 카메라

- 확인: 사용자가 숫자 선택 → 렌더 안정화 → 이미지·정답 저장을 반복하는 학습 생성 모드와 모든 CP 숫자가 왜곡 없이 보이는 중앙 카메라를 요청했다.
- 결정: 기존 Play는 순차 동작 확인용으로 유지하고, 새 `training_capture.py`에서 생성용 Stage의 자동 Behavior를 비활성화한다. 각 Slot 숫자를 선택한 뒤 Replicator `step_async(delta_time=0.0, rt_subframes=..., wait_for_render=True)`로 고정 상태를 반복 렌더한다. PNG·Crop·정답 파일이 완료된 후 다음 숫자로 진행한다.
- 카메라: `/World/Cabinet/Panels` 실제 경계를 기준으로 정면 중앙 직교 카메라를 계산하고 메인 USD에 `training`으로 추가한다. 4K, 사방 5% 여백, 투영된 숫자 Mesh 기반 Crop을 사용한다. 이유는 모든 숫자의 기울어짐·거리별 배율 차이와 잘림을 줄이기 위함이다. 실측 카메라 재현이나 실제 영상 분포 일치는 주장하지 않는다.
- 샘플링 가정: `0.0~999.0`에서 정수부 1·2·3자리 각각 14개를 Slot에 무작위 배정한다. Seed와 프레임 번호로 재현하며 실제 설비 값 분포는 미확정이다. Light·Material·Camera 랜덤화는 다음 범위로 남긴다.
- 안정화 가정: 최소 32 subframe 후 8개 단위로 비교, 모든 Slot ROI의 평균 RGB 차이가 두 번 연속 3/255 이하이면 저장한다. 초기 2/255 기준은 고정 상태에서 160 subframe까지 약 2~2.5의 변동이 남아 실패했으므로 예비 허용치를 3으로 조정했다. `0.0 → 999.0 → 0.0` 별도 잔상 검사와 25% 복귀 기준은 유지한다. 이 수치는 렌더 안정화용이며 OCR 학습 효과의 합격선이 아니다.
- 영향: 출력에 Seed·Config·실제 카메라/렌더 설정·코드/Asset Hash·Commit·설치 버전·subframe 검사 결과를 기록한다. FAILED Run은 제외한다. Split은 unassigned이며 동일 전체 프레임의 Crop은 함께 분할해야 한다. 기존 고정 픽셀 ROI와 다른 기준이므로 Real 비교용 ROI를 덮어쓰지 않는다.

## 2026-10-01 — 메인 USD의 Play 버튼으로 숫자 실행

- 확인: 사용자가 `press_cp_main`을 Isaac Sim에서 열고 Play로 실행하는 방식을 요청했다.
- 결정: `/World/DisplayPlayback`에 `OmniScriptingAPI`를 적용하고 `press_cp_play_behavior.py`를 상대 경로로 연결한다. Play/Pause/Stop 이벤트는 설치된 Behavior Scripting Core 110.3.0의 공식 생명주기를 사용한다.
- 동작: Play에서 최초 준비 후 순차 증가, Pause는 값 유지·재개, Stop은 `0.0` 초기화. 실행 중 카메라나 Stage를 교체하지 않는다. 표시 Mesh와 조회용 문자열은 SessionLayer/Fabric에 적용한다.
- 이유: 사용자가 Scene을 직접 열어 표준 재생 버튼만으로 실행할 수 있어야 한다. 별도 실행기는 같은 Mesh 작성 함수를 재사용하되 자동 Behavior를 비활성화해 두 제어기가 겹치지 않게 한다.
- 영향: 일반 GUI는 NVIDIA의 스크립트 실행 허용 절차를 유지한다. Windows CP949 의존성 스캐너 오류 때문에 진입 파일만 ASCII로 작성하고 한국어 구현은 표준 import로 분리한다. 실제 검증 프로세스에서만 로컬 Scene 실행 허용 설정을 잠시 적용하고 복구한다.
- Timeline에 유효한 0~60,000 time code 범위(60 fps)를 부여한다. 이 범위는 앱 재생용이며 숫자 간격은 Config의 실제 경과 시간 기준이다. Kit이 Play에서 추가하는 PhysicsScene·렌더 EcoMode 속성과 숫자 코드의 SessionLayer 변경을 구분하며 원본 파일을 자동 저장하지 않는다.

## 2026-10-01 — 학습용 ROI보다 연속 숫자 실행을 먼저 구현

- 확인: 사용자가 실제 `0.0 → 999.0` 연속 변화 기능이 필요하다고 지시했다. 기존 선택값 캡처는 이를 제공하지 않았다.
- 결정: 숫자 Mesh를 미리 준비하고 Fabric 계층의 로컬 Matrix로 숫자의 선택·배치를 갱신한다. 숫자 변경마다 RTX 누적 영상을 초기화한다. 실행 Stage는 시작할 때 한 번만 구성한다.
- 이유: 갱신 결과가 실제 렌더에 반영되어야 하며 값마다 Scene을 다시 여는 캡처 경로는 연속 실행에 부적합하다. 최종 구현은 같은 Stage에서 42개 Slot의 영상 변화·상한 순환 검사를 통과했다.
- 가정: 기본 0.1초 간격과 42개 Slot 동기화. 간격은 Config로 변경하며 실측 갱신 주기나 하드 실시간 보장을 의미하지 않는다. 부하로 늦어지더라도 숫자를 건너뛰지 않는다.
- 영향: 기존 캡처 경로는 유지한다. 연속 실행은 시작·중지·상태 조회·재개 API를 제공하며 Fabric의 일시적 표시 상태는 원본 USD에 저장하지 않는다. 학습용 ROI와 캡처 최적화는 후속 작업이다.

- 이유: USD 메타데이터 검사만으로 이미지·정답 동기화를 보장할 수 없었다. 최종 7개 프레임·294개 Crop은 렌더 변화와 42개 Slot의 `0.0` 복귀 검사를 실제 통과했다.

- 조건: 수동 조정된 원본 Camera는 보존하고 ROI 기준 Config 카메라를 캡처 Session Layer에 적용한다. 생략된 Bloom 값은 메모리에서 복원한다. 저장 조건과 실제 적용 조건을 모두 보고한다.

## 2026-10-01 — Slot 숫자는 자체 발광 재질과 렌더러 Bloom으로 표현

- 확인: 기존 숫자 Mesh에 Emission은 이미 있었으나 실영상보다 밝고 노랗게 보였으며 렌더러 Bloom은 명시되지 않았다. 4초 프레임의 42 Slot Crop에서 색·경계·배치 차이를 확인했다.
- 결정: 세그먼트 Mesh에 발광 색·세기를 별도 Config 값으로 적용하고 FFT Bloom으로 광학 번짐을 표현한다. 외부 조명 없이 Emission 켬/끔 대조 렌더로 실제 자체 발광을 검증한다.
- 이유: 숫자 모양을 이루는 발광 면과 카메라에서 보이는 번짐을 따로 제어해야 한다. 이번 범위에서 숫자마다 별도 점광원을 추가할 관측 근거는 없다.
- 영향: Scene의 renderSettings에도 값을 저장하고 재열기 시 적용값을 확인한다. Bloom은 화면 전체 후처리이므로 HMI 등 다른 밝은 부분에도 영향을 준다. LED 광도·소비전력·주변 조도와 같은 물리 측정값을 복원했다는 뜻은 아니다.
- 데이터 분할: 사용자가 현재 Train/Test 구간이 미정임을 확인했다. 4초 프레임과 추후 보정에 사용한 구간은 최종 Test 선정 시 제외·분리 대상으로 기록하며, 이번 설정은 예비 외형 보정값으로 유지한다.
